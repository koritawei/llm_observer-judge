### CMD 判定统一准则

1. **CMD 输出状态**：CMD 是否输出、缺失、误发或冲突，只以 `{{cmd_list}}` 为准；`cmd_list` 非空表示最终已向端侧输出 CMD，`cmd_list` 为空表示未输出 CMD。
2. **工具调用信息边界**：`{{tool_calls}}` 中可能包含 cmd 相关工具名、参数或返回内容，但这些只表示 Agent 内部调用过程，不能用来判定最终是否输出 CMD。
3. **CMD 参数准确性**：优先核对 `cmd_list` 中实际输出给端侧的字段（如起点、终点、途经点、操作类型等）；若路线偏好、规避道路、特殊定位、提槽参数等未完整体现在 `cmd_list` 中，才结合 `tool_calls` 中对应工具参数进行验证。
4. **端指令冲突硬条件**：单轮单 query 最多只能有 1 条端指令；出现 2 条或更多端指令（即 `cmd_list` 元素个数 ≥ 2）视为端指令冲突，端侧无法唯一执行，直接判 0 分。
5. **机场/火车站路线节点消歧优先级**：对 query 中作为终点或途经点的每个机场/火车站节点，先按 query 判断其指代是否存在歧义。节点仅表达泛称或未唯一指定机场/火车站主体（如“导航去机场”“去火车站”）时，必须先询问用户要去哪个节点；若 `tool_calls` 提供多个有效主体候选，应展示候选供用户选择，不得下发路线 CMD。节点已唯一指定机场/火车站主体（如“导航去首都机场”“去北京南站”）时，可继续规划或导航；即使 `tool_calls` 返回同一主体下的多个航站楼、出入口或附属 POI，也不得仅据此要求消歧。该要求优先于场景的默认 CMD 输出预期。

### 常见 CMD 参数校验参考

- `param_type`：`1` 表示进入导航；`0` 表示仅规划路线。用户说“导航到”“开始导航”等明确导航意图时应为 `1`；用户说“怎么走”“看一下路线”“多远”等路线问询时应为 `0`。
- `param_type1`：`-1` 表示默认；`2` 表示躲避拥堵；`4` 表示少收费；`8` 表示不走高速；`16` 表示高速优先；`32` 表示大路优先；`64` 表示速度最快。用户未提及路线偏好时应为 `-1`，若 query 中出现路线偏好或规避要求，应核对该值或工具参数是否正确承载。
- **路线偏好无枚举值回退**：若用户提及的路线偏好（如“红绿灯最少”）在 `param_type1` 中无对应枚举值，必须结合 `{{tool_calls}}` 中 plan_route 等工具的参数验证偏好是否已正确承载；仅当 `cmd_list` 与工具参数均未承载时才可判定偏好丢失。禁止仅因 `cmd_list` 无对应字段就判定偏好丢失。
- 道路规避/偏好、特殊定位、途经点、终点等关键字段应优先从 `cmd_list` 已输出内容核对；若未直接体现在 `cmd_list` 中，再结合 `tool_calls` 中对应工具参数核对。
