### 上下文与证据边界

1. **已提供的上下文**：仅指 input 中显式给出的用户 query、当前轮次，以及 output 中的 `cmd_list`、`component_text`、`env`、`history`、`user_profile`、`tool_calls`、`dto` 等显式信息。
2. **事实支撑来源**：POI 名称、地址、距离、评分、营业状态、价格、电话、标签、路线参数、绕行时间/距离等事实，必须能从 `tool_calls`、`dto`、`cmd_list`、`env` 或 `history` 中找到支撑。
3. **保存地点别名解析**：当 `tool_calls` 中出现 `saved_place_resolution` 时，它是“家/公司/单位”等保存地点别名到真实 POI 的解析证据。评估终点是否正确时，应同时核对 `alias`、`resolved_name` 与 `poi_id`；若用户说“导航回家/去公司”，总结文本使用别名而 `cmd_list` 使用真实 POI 名，只要 `poi_id` 与 `saved_place_resolution.poi_id` 对齐，不应判定为终点错配。
4. **总结文本边界**：`component_text` 是 Agent 的对用户表达，可作为“Agent 声称了什么”的证据，但不能反向充当外部事实来源。
5. **作用对象拆解**：判断事实或约束是否满足时，必须先确认条件作用对象；不得把附近/周边/沿途/目的地附近等附属条件错套到主目标 POI 本身。
6. **未证实条件**：未证实条件不等于事实虚构；只有 Agent 明确声称某条件已满足，但上下文无法支撑或工具数据相反时，才按事实或约束错误扣分。
7. **强弱证据分层**：POI 名称、品牌字段、类别、标签、运营方、工具结构化属性、CMD 实际输出字段、明确数值字段属于强证据；地址中的周边地标、门牌参照、对面/旁边/附近/隔壁/路口等空间关系描述属于弱证据。弱证据不能单独推导强结论。
