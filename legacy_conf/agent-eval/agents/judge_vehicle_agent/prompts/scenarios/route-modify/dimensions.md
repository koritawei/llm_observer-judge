## 场景专属规则

本节只描述 `route-modify` 相对通用前置规则与全局 D0-D6 规则的补充项；未覆盖项按公共规则判断。

### 场景专属硬条件

- D4: 必须满足当前预期输出形态；预期改路执行但 `cmd_list` 为空，按 D4 执行闭环失败处理；不要求输出 Markdown 的轮次不得因 Markdown 缺失扣分。
- D1: 未识别为基于当前路线的修改意图，或错误触发新搜索、新导航、路线问询，按 D1 失败处理。
- D1: 规避/偏好的道路、路线策略、道路限制或特殊定位的用户意图识别错误，按 D1 归因。
- D2: 规避/偏好的道路、路线策略、道路限制或特殊定位未被正确满足，按 D2 归因；导致路线修改不可用时判 0 分。
- D2: 多个路线策略或道路约束并存时，遗漏任一关键约束或把规避/偏好方向反向处理，按 D2 归因；破坏改路目标时判 0 分。
- D4: 多个路线策略或道路约束并存时，CMD 参数未覆盖或反向处理，按 D4 归因；破坏改路目标时判 0 分。
- D3: 总结文本声称已采纳某道路或路线策略，但 `cmd_list` 或 `tool_calls` 无对应参数支撑，按 D3 归因。

### 专属维度覆盖

- D1：重点看是否正确识别为改路/路线策略调整，而不是重新搜索、普通导航或路线问询；还需识别规避、偏好、最短、最快、少收费、不走高速等意图。
- D2：重点看道路名称、规避/偏好方向、多个路线策略和原路线继承是否正确；用户要求“走某路”和“不走某路”必须区分。
- D3：重点看已采纳道路、路线策略、路况原因和执行结果是否有 `cmd_list`、`tool_calls`、`env` 或 `history` 证据；不得声称采用未实际传入的策略。
- D4：重点看是否产出唯一、可执行、动作类型正确的改路 CMD；字段错误、漏发、误发或错误覆盖原路线优先归因 D4。
- D5：总结文本如存在，应简洁确认已调整的道路/策略，避免表达成新导航、普通搜索或未执行的建议。
- D6：纯改路执行类不要求主动补充距离、耗时、评分等信息；只有存在冲突、不可达、需选择或无法完全满足时才适用。
